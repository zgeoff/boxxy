# Tuning proposal, November 2026

Five changes to how boxxy runs work, from what went wrong on 2026-11-17 and 2026-11-18. Each one
lists the evidence, the change and its cost. The owner picks which to build; nothing here is filed
as an item yet.

## What happened

Across the two days, boxxy built five pull requests: stu#5, stu#6, stu#8, noslop#342 and boxxy#156.
Four merged, all by hand. Items stopped for the owner more than ten times. Most stops came from the
five gaps below, not from the work.

## 1. Split acceptance into build checks and landing checks

**Evidence.**

- The watcher item (`01a1d3d5`) blocked three times on a17, a live run with `systemctl --user` on
  the owner's PC. Each review round changed the notifier, so each new head needed the run again.
- The licence item blocked on "GitHub lists the licence", which GitHub shows only on the default
  branch, so no pull request can show it.
- The skills-folder fix (`01a1e8f2`) blocked on "a build in zgeoff/skills binds its session", which
  only a deployed release can show.

Each builder was right to block: the brief asked for evidence the sandbox can't produce.

**Change.** Give each acceptance line a `stage`: `build` (the pull request proves it, and the build
can't close out `built` without it) or `landing` (it runs after merge, or on a machine the sandbox
can't reach). A builder writes the steps for a landing check into the pull request and never blocks
on it. Triage sets the stage. Landing checks run after the merge phase, by an agent where one can
reach the target, or they go to the owner as one batched notice.

**Cost.** A contract change: one field on `AcceptanceLine`, the triage prompt, the build prompts'
close-out rule, and a landing step after merge.

## 2. Turn on the merge phase

**Evidence.** Five pull requests sat green and reviewed overnight on 2026-11-17, waiting for the
owner to say "merge them". The [merge step](./review-and-merge.md#the-merge-step) is already built
(slices 8 and 10 of the [next work list](./next-work-list.md)), but the live rules in
`zgeoff/boxxy-rules` run no merge phase.

**Change.** Add the merge phase to the pipelines in `rules.yaml`, with `merge.checks` per repo. Keep
the owner's review where it matters: a rules list of paths whose pull requests hold for the owner
before merge, such as `skills/**`, `**/SKILL.md` and the rules repo's `prompts/`. Today the owner
grants that by hand each session.

**Cost.** A rules change, plus the path-hold list if the merge rule lacks one. Review becomes the
only gate before merge, so change 4 matters more.

## 3. Route owner-only items straight to the owner

**Evidence.** Triage turned "trust stu's Codex hooks with `/hooks`" into a chore whose Permissions
said an agent does no work. boxxy still started a build, which blocked after 50 seconds and asked
the owner. Both `needs-owner` holds on 2026-11-17 were technical calls the triage prompt already
says to decide: the unused `stuKnows` field, and which repo a synced skill's fix belongs in.

**Change.** Let triage close out an item as `owner-task`: it holds for the owner with the exact
step, and no build attempt starts. Track the share of `needs-owner` holds that the owner answers
with "decide it yourself", and tighten the triage prompt when that share passes one in five.

**Cost.** One close-out kind and one hold reason; a prompt line in triage.

## 4. Check a design's claims about other systems before the build

**Evidence.** The watcher's design named `atc.sock` as atc's client socket. It's the hook reporter
socket; the client socket is `atc-daemon.sock`. Tests faked the socket with the design's name, CI
passed, and the fault showed only in the live run on the owner's PC. That cost one full round
trip.

**Change.** In the design prompts, require each socket, endpoint, CLI flag or API that the design
names in another system to be run against that system's current build, with the output kept as
evidence. The build prompt adds: drive the real dependency once where the sandbox can reach it.

**Cost.** Two prompt changes. Designs take a little longer.

## 5. Give review a second model family again

**Evidence.** Every build's close-out runs `codex review --base main`, and each one failed with 401
on the runners, so every build fell back to a Claude subagent. The noslop review is Claude too, so
no change had a review from another family.

**Change.** In progress on 2026-11-18: the geoffcloud daemon gives the `boxxy` agent the brokered
`codex` sign-in. Once it's live, the fallback should stay rare; record which model reviewed in the
close-out, so a silent fallback shows up in pepys.

**Cost.** Done in the cloud repo, apart from the close-out field.

## Order

1 and 3 remove most of the owner's stops, and 2 removes the merges. Build 1 first, since 2 is safer
once landing checks exist; then 3; then 2, which is a rules change; then 4 and the field in 5.
